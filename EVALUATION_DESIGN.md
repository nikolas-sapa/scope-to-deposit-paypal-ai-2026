# Evaluation design

This is the frozen evaluation protocol. The table retains its original proposed baseline statuses; [RESULTS.md](RESULTS.md) is the current acceptance ledger. T05/T15 now pass with genuine Sandbox evidence. The October 16 real-model T01 baseline failed; T14 is incomplete. This document defines evidence and pass criteria without selecting routes, dependencies, persistence, or a final data schema.

## T01 scope extraction

Use exactly the 20 `SYN-*` cases in `fixtures/synthetic-briefs.json`. Freeze fixture version, rubric, model identifier, prompt, and run configuration before a real configured-model run. Score each brief independently against its source-grounded expected facts. Required fields: goal, deliverables, explicitly stated timing, constraints, assumptions, questions. Preserve absent values as null/empty and ask the listed blocking questions. Do not reward inferred facts. Mark every labeled ambiguity as detected only when output explicitly flags it and asks for resolution. A case passes only when every stated fact is correct, every absent/ambiguous value remains unresolved, and no commitment is fabricated. **Target: at least 18/20 case passes, 100% of labeled ambiguities detected, zero fabricated commitments.** Report per-case counts and denominator 20. Fixture-only or mocked runs are diagnostic and never satisfy T01.

## Test protocol

Each result must identify mode: `LOCAL_FIXTURE`, `REAL_MODEL`, or `REAL_SANDBOX`. `LOCAL_FIXTURE` means the genuine running local application with synthetic data; separately record whether provider calls or authentication/webhook verification were mocked. It implies no provider evidence. `REAL_MODEL` means the approved model actually generated output; `REAL_SANDBOX` means a real PayPal sandbox interaction. Mocks and simulations must be labeled and cannot be presented as provider evidence. Record every test result as `NOT RUN` until evidence exists. A passing test requires all assertions below and a complete evidence record; partial samples remain not run or fail, never pass.

The same genuine retained artifacts may support multiple tests when each criterion is independently evidenced; do not repeat transactions solely to produce duplicate artifacts.

## Evidence manifest proposal

One record per test run, with per-case or per-scenario references where needed. Suggested fields, not a committed schema: `test_id`, `run_id`, `mode` (`REAL_SANDBOX` / `LOCAL_FIXTURE` / `REAL_MODEL`), UTC timestamp, result (`PASS` / `FAIL` / `NOT_RUN`), actual count, expected count/criterion, redacted IDs, evidence references, and notes describing limitations or fault injection. For local runs, record separately whether provider calls and authentication/webhook verification were mocked. References may be reused across tests when the artifact independently proves each criterion. They should point to retained artifacts such as rubric/output/scoring, redacted provider response, state history, scanner report, transcript, or screenshot. Redact credentials, access tokens, buyer passwords, session secrets, and unnecessary personal data. IDs are redacted identifiers, not secrets. A missing artifact, unavailable prerequisite, or mock-only result cannot be upgraded to a real pass.

## Fixture versus live evidence

The JSON fixtures are synthetic source material and expected semantics. In each case, `expected_semantics.questions` and `blocking_questions` are rubric expectations authored for missing or ambiguous source facts; they are not claims that the brief itself stated those questions. `missing_fields` contains a boolean for all six required output fields; `questions: false` means the expected output field exists (its list may contain blocking questions). Timing preserves only source-stated timing, even when relative or ambiguous; absent deadlines stay null and event dates do not become delivery dates. All monetary hints are user text and untrusted, never authoritative. Fixtures can test rubric clarity and local validators; they cannot show model quality, payment behavior, identity controls, webhook authenticity, production readiness, or user outcomes. Mocks can validate expected local branches only. REAL_MODEL requires the human-approved provider/model/budget gate. REAL_SANDBOX requires approved credentials, buyer/merchant identities, and provider evidence. Those were the original fixture-preparation conditions. Current provider results, confirmed entrant declarations and remaining access prerequisites are recorded in RESULTS.md. Private credentials are excluded from this protocol.
